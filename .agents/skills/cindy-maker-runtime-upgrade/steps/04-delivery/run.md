# 04：打包、安装到 Cindy 并交付

本步沿用前三步已经核验的候选和证据。第三步需要的验证未完成时可以准备包，
但不能把最终安装验收标为通过。仅在本次范围包含安装时执行安装；
若用户只要求本地适配，交付到该范围并明确未安装，不自动延伸到发 PR/发布。

## 1. 产物必须包含这次改动

优先使用当前 Cindy 已提供的本地插件打包/安装能力，按实时工具发现及插件编写 Skill
执行。不猜工具名，也不通过修改应用文件/数据库绕过安装。没有此能力时使用仓库既有包格式。

插件仓的标准脚本：

```text
bash .github/scripts/package-plugin.sh taptap-maker <仓库外输出路径.cindy>
```

**它归档 HEAD:taptap-maker，不包含未提交改动。** 尚未获准 commit 时，不为让脚本
带上改动而提交；也不能把 HEAD 的旧包当成新包。可以用 Host 的工作目录打包能力，
或按当前脚本契约在仓库外制作工作树验证包：

1. 收集完整插件目录中的受审文件与必须的根法律文件，包含未改动文件，排除 .git、
   node_modules、证据/旧包/凭证；核对新增与删除，不只打包本轮改动文件。
2. 复用 git archive 能力时可用独立 GIT_INDEX_FILE：read-tree HEAD，
   将已核对的本轮文件路径加入临时索引，write-tree 得 tree，然后 archive 该 tree 的
   taptap-maker 子树并加入根法律文件；不写真实索引、不创建 commit、不改分支。
   沿用标准脚本的 git -c core.autocrlf=false archive，特别检查 Windows 换行；
   对包内文件按 recipe.vendorHashes 复核，不能只对工作树源文件算哈希。
3. 或使用当前项目支持的工作树打包实现；不要仅压缩整个目录导致遗漏法律文件或带入垃圾。
4. 按标准脚本核对 ZIP 普通文件、无目录记录、文件数、解压后体积及压缩体积。
   当前 Node 包上限为128MiB压缩/256MiB解压/256个文件；以执行时仓库契约为准。
   Windows 工具见 [平台说明](../../references/platform.md)。

解包最终 .cindy 检查 ghost.json/version、vendor/package.json、maker.js 和完整 vendorHashes、
node adapters、Manual/locales、LICENSE/NOTICE/TRADEMARKS/THIRD-PARTY-LICENSES。
记录包 SHA-256，不能只核对文件名。

## 2. 安装和确认实际执行来源

1. 记录 Cindy 实际版本、系统、架构和渠道。用满足插件要求的正式/Beta 宿主；
   渠道无法确认就如实记录，不能从包名/开发构建推断。
   安装前记录原插件来源/版本及 Host 支持的恢复途径；新包出现主链路回归时停止测试，
   保留证据并按该途径恢复。宿主不支持降级时如实说明，不直接替换应用文件或数据库。
2. 安装/原位更新本包，核对 Host 回执的插件 id、实例、版本、来源。取消/拒绝不算安装；
   MUTATION_CANCELLED 后不能把旧插件调用算新包验收，也不自动反复发起确认。
3. 核对安装文件与本包内容/哈希一致。检查与同机 standalone Maker MCP 的入口差别，
   通过真实 ghost_info/ghost_call 对已安装 taptap-maker 调用，避免测到同名独立 MCP。
   不为此卸载/禁用其他 Agent 的 MCP。
4. Console 不因安装自动换进程。只关闭已确认属于本次的旧测试实例，确认退出/端口释放，
   再通过新安装插件打开，核对新 instanceId/入口/版本，防止旧服务继续提供旧画布脚本。

## 3. 宿主中的功能验收

先检查用户已指定测试项目和授权；项目工具只认可信工作区，不从插件仓伪造另一个
target_dir。必要时使用已绑定测试项目的 Cindy 任务；执行上下文确需改变且无法自行
切换时说明原因，不绕过门禁。无需游戏目录的入口先继续验收。

| 范围           | 必做基础检查/按差异补测                                                                                                                                   |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 安装和基础调用 | maker_status/doctor/list_tools/ads_guide；实际 Runtime 目标版本和托管状态正确，插件仓 unbound 不冒充游戏测试                                              |
| Console/设置   | maker_console 及设置页入口实际打开；Server-only 策略、模型入口、loopback、locale、媒体/预览开关及保存错误按差异验收                                       |
| 画布/UI 编辑器 | 打开真实测试项目已有画布、UI 文件和 Git 页面；核对卡片、节点树/属性、实际下发脚本。涉及编辑/持久化时在副本做授权的修改、保存、关闭重开，不能只看 HTTP 200 |
| Host 特有兼容  | Electron stdio/childSpawn、进程退出、roots 项目切换、Console 所有权按本轮差异验证；Windows/macOS 分别记录，不以另一平台模拟替代                           |
| 预览/验证      | 本轮接入或变化涉及此链路时，从已安装插件完成实际游戏及证据交付，核对第三步同一 bundle；UNSUPPORTED 只证明拒绝，打开窗口只证明启动                         |
| 账号/付费/生产 | 换 PAT、受限账号、克隆、云端提交、远端 build、媒体生成只执行本轮明确授权且必要的场景；其余用定向故障模拟并标缺口。不为拿“全功能通过”制造扣费              |

若安装后又改了 recipe/vendor/adapter，重跑受影响自动回归和第三步场景，重新打包/安装
并核对哈希；最终证据指向最终包。不要把 V9 包的成功直接算作后续 V10 包全部通过。

## 4. 交付及可选的提交发布

读取 [04 验收](acceptance.md)，按本次记录直接回复：升级到什么、保护逐项处置、
本机 CLI/真实游戏/Cindy 各测了什么、最终包在哪里、还有哪些具体缺口。
不只给文档链接，不宣称所有平台/付费故障均已验证。

任务包含 commit/push/PR 时，接着按需读取 [第五步操作](../05-pr-review/run.md)，
完成后再读其独立验收；未包含时到此交付。前四步的通过记录和包哈希交接给第五步，
审核导致行为变化时按影响返回对应步骤，不重读和重测无关部分。

合入 main 是向 Global 平台提交包，审核后可见；不恢复 CN 推包。
本工作流不授予发布权限，也不把普通 vendor 升级一律变成人工审批。
