# 05：提交 PR 与逐轮处理审核（按需）

仅任务包含提交/PR/审核跟进时读取。沿用本次明确授权，不因工作流自动执行 commit、
push、发评论、Resolve、请求 reviewer 或 merge；也不重复索要已有授权。
只读审核可直接进行。单纯“查看状态”不等于授权对外回复或修改线程。
历史案例按需读 [10 月 PR 处理记录](../../sources/pr-review-lessons.md)。

## 1. 创建或更新前核实目标

1. 使用插件仓当前 AGENTS.md、.greptile/rules.md 和 .greptile/config.json；本轮已读且
   内容未变就不重读。历史中的固定实机勾选、全量 vendor 一律人工审等口径不能照搬。
2. 核实官方仓库、目标 main、来源 fork 关系、head 分支/完整 SHA、PR 编号与 OPEN/
   MERGED/CLOSED/Draft 状态。下一轮升级从最新官方 main 新开分支，保留已有工作；
   不把新提交推到已合并 PR 的旧分支。身份与远端权限看当前登录/API，不从 Git author 猜。
3. 复核前面记录的版本仍大于最新 main；仅有版本疑问时再查市场/安装来源，不能凭
   本机装过某版本跳号。PR 标题/正文、manifest 和最终包按实际语义同步。
4. 提交前再次检查当前分支是本轮升级分支而非 main，且未对应已合并 PR；push 显式指定
   已核实的 remote 和本轮 head 分支，禁止直接推送 main。执行当前仓库要求的检查，
   核对包版本、依赖许可证、双语文档、四语言语义。
   用 Conventional Commits、说明用途与验证的 bullet body、匹配作者的 DCO sign-off。
   DCO 以 GitHub **该 PR 实际 commit 列表**或 DCO check 为依据，不能拿本地/沙箱 log 定罪。
5. 有未完成项且用户允许先提 PR 时建 Draft，正文列明失败与缺口。正常进入正式审核前
   补齐必要验收；Draft 跳过的检查不算通过。PR 创建失败先查远端收据与现有 PR，
   不因 422 或中断反复创建、重复推送/发评论。

优先使用可用的 GitHub 插件，或原生 gh/GitHub API。核实当前 ruleset/分支保护，
不能把历史“一份 approval”写死；状态摘要不能代替完整 review、线程和普通评论。

## 2. 把意见变成可核实的处理清单

以当前 head 为准，把自动 reviewer、人工 review、行级线程、普通评论和已知未完成项
合并去重，分页读取完整内容，填入 [本次记录](../../templates/run-record.md) 的 PR 表。
每条保留链接、适用 SHA、触发条件/实际影响与依据；线程为零也要查普通评论。

确认缺陷以复现或调用链/协议证据为依据；环境失败须与基线对照，不掩盖本次新回归。
验证缺口写明具体场景；有据不采纳引用当前需求、实现或替代提交。真实边界决定与平台
授权等待按现行契约单列，仅实际涉及时处理；前面核实且仍适用的结论直接引用。
下载/凭证等意见返回 [2F 清单](../../compatibility/06-package.md) 核对，不在本步重做审计。

不要为关闭意见删除功能、恢复旧契约或削弱门禁；真实功能取舍取得相应决定后，
同步实现、说明与测试。来源不明的判断不写成结论；已发出的不实诊断须在 PR 原文及
相关评论中明确更正，保留实际现象、已证明范围和未知项。

## 3. 修复、补证据、回复和 Resolve

1. 审核新增兼容修复回填第二步清单、配方与历史来源；尚未提交用文件/配方 ID，
   有真实提交后再补 hash，防止下轮整包替换丢掉补丁。
2. 按影响返回第二至四步：行为补丁跑定向回归及仓库必需检查，相关 CLI/真实游戏/
   Cindy 路径重测；包内容变化重新打包核哈希。运行内容变化需重新安装并验证相关路径。
   不受影响的证据可复用，但说明从已测版本到当前 head 的**全部差异**为何不影响它。
   纯说明改动不机械重跑所有游戏场景。
3. PR 正文同步最终来源、版本/配方、包证据、Cindy 环境、实际验证和未测范围；
   引用前四步证据即可，区分模拟/真实进程/宿主及不同截图路径，不重复抄 CI 已有哈希。
4. 在获准跟进审核的范围内，逐条回复“结论、修改位置/提交、验证、剩余边界”；
   用 PR 作者主语言。确认已修复并有对应证据，或意见已被证伪/撤回后才 Resolve。
   仍有实质争议时保留状态并给出依据；普通评论没有 Resolve 动作，回复并登记处置即可。
5. 推送后重新读当前 head 的 CI 和新审核。意见过时不等于修复；检查新旧问题是否同根。
   不固定审核轮数，也不无变化反复催同一决定；新证据到来继续处理，已证伪/已解决的
   问题无新证据不重新打开。

## 4. 报告当前状态，不提前宣称只差批准

结束前重新核对最新 head、所需 CI/DCO、仍在运行的审查、有效 approving review、
冲突、未解决线程、普通评论未结事项、已知缺陷、验收缺口及相关决定/平台等待。
新 head 使 review/检查失效时按实际门禁重查；GitHub UNKNOWN/数据未取全写“待确认”。
不要把“无评论”“线程为零”“CI 绿灯”“审查分数”互相等同。

读取 [05 验收](acceptance.md)，向用户给出当前 PR/完整 SHA、已处置项和最小剩余待办，
区分等执行者补修复/验证、等维护者决定/有效 approval、等平台批准或宿主发布。
只有其它必需事项都满足，才说“只差有效 approval”；有审查仍在运行时明确标出。
授权的跟进期间完成可执行工作，不仅报待办后停下；外部等待则如实交接，不承诺后台驻守。

合并仍须当前规则、有效批准、运行证据和线程处置满足，并有相应执行授权及权限。
不自批、不绕保护、不因 review 身份自行 merge/close。合并、Global 平台提交、
平台批准、市场可见是不同状态，按真实收据报告，不把 PR 合并写成插件已上架。
